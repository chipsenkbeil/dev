## .dev scripts

One script per verb (`install.lua`, `uninstall.lua`, `restow.lua`, `purge.lua`, `clean.lua`, `list.lua`, `stow.lua`, `sync.lua`, `setup.lua`, `skills.lua`, ...) run through `dev <verb>`, and the subdirectories `pi/` and `antinote/` hold the Lua subcommands of `dev pi` (`install`, `save`, `diff`, `check`) and `dev antinote` (`export`, `import`, `diff`), over `.dev/lua/dotfiles/pi.lua` and `antinote.lua`. `lint.lua`, `fmt.lua`, `test.lua`, `soak.lua` and `skills.lua` are Lua verbs that run in the dev process (see the `dev.*` bullet above). The install family is `.dev/lua/dotfiles/packages.lua`: `default_deps` (the single source of truth for the default targets), `select` (the package arguments, or the defaults), `ensure_stow` (runs `scripts/install-stow.lua`, the pinned build, into `DEV_TOOLS_PREFIX` else `~/.local` when stow is not on `PATH`, and the stow calls after it use that prefix's binary), the stow flag table (`--no-folding` for `gpg`, `ssh`, `bin` and `pi`, plus `--ignore='settings\.json'` for `pi`) and the per-package hooks (`gpg`, `ssh`, `antinote`, `pi`, `claude`, `jj`), so any `dotfiles/<app>/` directory is automatically installable. `SRC_DIR` (default `<repo>/dotfiles`) and `TARGET_DIR` (default `$HOME`) come from the `KEY=value` arguments, then the environment, so a test points both at a temp tree. The `pi` and `antinote` hooks call `dotfiles.pi` and `dotfiles.antinote` in process. `tests/lua/packages_test.lua` pins the module. `.dev/sync.lua` is the project's `dev sync` (it wins over the built-in lint-template `dev sync`, so `dev __flags sync` offers none of `--check` and `--yes`): it takes `SYNC_DST` (`user@host`) and `SYNC_PATH` (the remote folder, `dotfiles` by default) from the `KEY=value` arguments, then the environment, and without `SYNC_DST` asks on a terminal and exits 1 without one. It pipes the NUL-separated output of `jj file list` (a `.jj` repo) or `git ls-files -z` into `rsync -azqP --from0 --files-from=-` through `dev.os.capture_input`, then runs `ssh <dst> "cd '<path>' && bash dotfiles/bin/.local/bin/dev install"`, so the remote `dev` finds its project from its working directory. The ssh output goes to a `dev.fs.mktemp` log that a successful sync removes and a failed one keeps (`sync failed; log kept at <path>`, exit 1). `dev sync SYNC_DST=host` and `SYNC_DST=host dev sync` are the same call, and `dev install nvim TARGET_DIR=/tmp/home` installs into a temp tree. `dev install`, `uninstall`, `restow` and `purge` take package names, and the other verbs take only `KEY=value`. `dev skills` calls `packages.fetch_skills` and takes no argument.

## The guide and scribe commands

### dev guide

A built-in verb in the "Set up a machine or project" group, and machine-local (`--remote` refuses it, and it refuses to run as root). With no question it prints the project's `overview` topic when `.dev/topics/overview.md` exists (rendered like any topic), then the curated `dev help`, as one text that always goes through the pager on a terminal, like the curated view (`DEV_PAGER=0` turns it off). With a question it runs `guide dev --context-dir <root>/.dev/topics -- <question>` from the repo root, so the project's topics are gathered before the rest of the help. It needs the `guide` package installed. The curated `dev help` has no verb-count cap: it is curated by purpose and fits a 50-line screen. `board` is shown under "Share it". The hidden verbs are `bootstrap` (machine-local setup run once), `help`, `gpgkeys` (the legacy GPG key listing) and dev's own `__` helpers, and `tests/dev/guide_test.sh` pins that exact list. `dev help -a` still lists them.

### guide

The `guide <tool> [question]` command. `.local/bin/guide` is a launcher: it finds `luajit` (else prints the install hint and exits 1), makes the work directory (`GUIDE_WORK`, which `main.lua` uses and the launcher's `EXIT`, `INT` and `TERM` traps remove, so `Ctrl-C` leaves none). luajit has no signal handler of its own, so the launcher runs it as a background child and waits for it (a foreground child would defer the `TERM` trap until it ended), the traps end the child and everything it started (a walk down `pgrep -P`) and exit 143 or 130, resolves its own symlink, sets `GUIDE_DEV_LUA` to the `dev` Lua modules (the dotfiles tree beside it, else `~/.local/share/dev/lua`), keeps the caller's `PAGER` in `GUIDE_PAGER`, its `NO_COLOR` in `GUIDE_NO_COLOR` and its `TERM` in `GUIDE_TERM`, exports `PAGER=cat`, `MANPAGER=cat`, `GIT_PAGER=cat`, `NO_COLOR=1`, `TERM=dumb` and `CLICOLOR=0`, and runs `luajit .local/share/guide/main.lua`. `.local/share/guide/*.lua` is luajit: `main.lua` holds the options, the checks, the cache and the scribe calls, `help.lua` parses a help text, `probe.lua` runs tools and the man page through `dev.os.capture_timed`, `tree.lua` reads the top of a help tree, `gather.lua` collects guides, help and the man page, and `check.lua` is the post-check. `main.lua` runs both as `luajit gather.lua MODE TOOL ...` and `luajit check.lua TOOL FILE` (gather exits 3 when the documentation is over the budget). A tool follows the help convention when `<tool> help --topics` exits 0 with at least one `name<TAB>summary` line, and guide then reads its commands from `help -a`. A question goes to `scribe guide-answer --profile guide` (prompts in `dotfiles/scribe/.config/scribe/prompts/guide-*.md`), and the answer is checked against the live help, one `warning:` line per made-up subcommand or flag. Everything guide prints as Markdown (an answer, and the cached or fresh overview) goes through `dev.ui.markdown` with the width capped at 100 when standard output is a terminal and colour is on, decided by `dev.ui.context` over the caller's `NO_COLOR` and `TERM`, read from `GUIDE_NO_COLOR` and `GUIDE_TERM` to survive the launcher's overrides. `progress.lua` draws a status line on standard error, `<label> (<N>s so far)` in dim, under the same rule (standard error a terminal, `GUIDE_NO_COLOR` empty and `GUIDE_TERM` not `dumb`), for each step of a run (reading the help and man page, choosing subcommands, asking the model, checking the answer). It is redrawn at each step, not ticked during one, since the steps block in capture calls, and erased when the step ends or fails, so only the answer stays. The launcher erases it on `INT` and `TERM`. A run with standard error piped, `NO_COLOR` set or `TERM=dumb` draws nothing. A pipe, `NO_COLOR` or `TERM=dumb` print the text unchanged. The post-check warnings are written after the rendered answer, one per line, and the offline help text is not Markdown and stays plain, except that on a terminal with colour `style_help` in `main.lua` bolds each help heading (a line ending in a colon with nothing after it, or all capitals at column zero) and cyans each flag that starts an indented line. It adds colour codes only. `--offline` has `gather.lua offline` print its parts (the guide list, each guide body, the help text) each after a mark line of the control character 0x1e and its kind, which `main.lua` splits. On a terminal with colour it draws the guide list as a `dev.ui.table` with bold names and each guide body through `dev.ui.markdown`, and a pipe, `NO_COLOR` or `TERM=dumb` print the parts joined, with the guide list tab separated and each guide body as written. The man page keeps its own marks: `probe.man_raw` caches `man -P cat` output with the overstrike text as it is, in the entry `man-raw` (an older build's stripped `man` entry is never read, so its page is fetched once), `probe.strip_man` removes the marks as `col -b` does, for the model's documentation, the post-check and a pipe, `NO_COLOR` or `TERM=dumb`, and `probe.style_man` turns `X` backspace `X` into bold and underscore backspace `X` into underline on a terminal with colour, one pair of codes for each run of characters with the same marks. The whole offline text, man page included, goes through `show` once, so the pager takes it as one text. A rendered answer or no-question overview, warnings included, goes through `dev.ui.page` with the caller's pager from `GUIDE_PAGER` (`less -R` when the launcher finds no `PAGER`) when standard output is a terminal and the text is taller than the screen, after the status line is erased; `--no-pager`, a pipe or a short text print it directly. Documentation over `GUIDE_BUDGET` characters (default 60000) takes a second model call, `guide-pick`, to choose the subcommands to read. With no question, a tool with no guides gets a model-written overview cached in `${XDG_CACHE_HOME:-~/.cache}/guide/<tool>/<hash of its version>.md` (`--refresh` rebuilds it, `--offline` skips the model). `probe.help` and `probe.man` keep each help text and the man page in `${XDG_CACHE_HOME:-~/.cache}/guide/<tool>/<hash of its version>.docs/` (`GUIDE_DOC_CACHE` names the directory for the `gather.lua` and `check.lua` children, `probe.use_cache` for the main process), so a second question about one version runs no `--help` probe, only the one `--version` call that makes the key; a probe that hit the time limit is not kept, `--refresh` removes every `.md` and `.docs` entry of the tool, and the `--context-dir` guides and the `help --topics`, `help -a` and `help -k` calls are never cached, since they can change without a version change. Every call to the tool has a time limit (`GUIDE_PROBE_TIMEOUT`, default 3 seconds, and 0 sets no limit, as in GNU `timeout`), runs in its own process group so the limit also stops what it started, and reads no stdin. The guide calls set `opts.reap`, which kills the group of a call that exits on its own, so a background child of a finished probe does not stay behind. `dev.os.without_sigpipe(fn)` makes a write to a closed pipe (a pager quit early, scribe exiting unread) fail instead of killing the process. `dev.os.capture_timed(argv, secs, opts)` is the timed call: it waits for the watcher to start with 5 millisecond `usleep` polls and then polls the status with 0.1 second ones (no `timeout` command, and no `sleep` in the loop, to keep `os.execute` from ignoring `SIGINT` while it waits), starts a watcher beside the command that blocks reading a pipe the calling process holds open (it starts no process while the command runs) and that, when the command has not finished, kills its process group, and in every case removes the temporary directory when the pipe reaches end of file, which happens when the calling process dies (`Ctrl-C`, `TERM` or `KILL`), sets no limit when `secs` is 0 or less, collects the output, merged with standard error when `opts.merge` is set, kills the process group of a command that exited on its own when `opts.reap` is set (scribe and `dev board check` do not set it), takes `opts.input` as standard input (else /dev/null), and returns the exit code, 124 when the limit hit or the command was killed. Tests are `tests/guide/guide.bats`, which put fake tools, a fake `man` and a fake model command first on PATH.

### scribe

The `scribe <kind>` command, the same launcher shape (`SCRIBE_DEV_LUA`). `.local/share/scribe/main.lua` holds the options, the settings and the flow, `profile.lua` walks a profile's `command` and `http` lines in order and returns the first answer, and `backend.lua` makes the curl chat call (the payload built by `dev.json`, only `.choices[0].message.content` read), runs a command backend through `dev.os.capture_timed` with the system prompt and context on its standard input, and cleans the answer (think-blocks, quotes and, for `*name`, `*slug`, `bookmark-*` and `branch-*` kinds, a kebab slug of at most 50 characters). Profiles and prompts are looked up under `SCRIBE_PROFILES` and `SCRIBE_PROMPTS` (default `~/.config/scribe/profiles` and `prompts`). `~/.config/scribe/config` is read as `SCRIBE_NAME=value` lines for any `SCRIBE_` setting (an optional `export`, one pair of quotes around the value) and wins over the environment. Tests are `tests/scribe/scribe.bats`, with a fake `curl` and fake commands first on PATH.
