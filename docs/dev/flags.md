# flags: The global flags, how help flags work, and how the launcher and dispatcher start dev

Five flags work anywhere before a `--` on the line, whatever the verb.

- `-v` or `--verbose`: print each command before it runs, and export
  `VERBOSE=1` to it.
- `-vv`: also trace every line of dev and of each bash script it runs, which
  exports `VERBOSE=2`.
- `--remote`: run the command on a remote runner, by default the verb's job of
  the same name from the project's default pipeline (`.ci/jobs.lua`) on
  example-box through ci. `DEV_REMOTE=1` in the environment is the same.
- `--local`: run the command here, whatever the `[remote] default` setting says.
  With `--remote` it is a usage error. A command with a ci job runs remote by
  default, so see the `remote` topic.
- `--detach`: with `--remote`, start the job and return. Alone it is a usage
  error.

`-v` and `-vv` also stack as `-vvv` (the count is capped at 2). Setting
`VERBOSE` in the environment counts the same, where empty, `no` and `false`
mean off and any other word means 1.

```
dev -v lint
dev -vv test
dev --remote test
```

`dev help remote` explains the runner, the refusals and how a project replaces
it.

## Help flags

`-h` and `--help` are reserved for help on every verb, in any position,
but only before a `--`. A script never sees them there, and so cannot
declare them in its `# flags:` line (`dev __topics check` reports one
that does). Everything after a `--` reaches the verb verbatim, so
`dev run -- -h` runs `cargo run -- -h`.

- `-h` anywhere after a verb prints its description, usage and flags.
- `--help` anywhere after a verb prints the long form, the same as
  `dev help <verb>`.
- `dev help -a` lists every command, hidden ones included.
- `dev help --topics` lists the topics, and `dev help -k <topic>` prints one.
- A topic taller than the terminal opens in `$PAGER` (else `less -R`).
  `dev help --no-pager <topic>` or `DEV_PAGER=0` prints it directly.
- The curated `dev help` always pages on a terminal, even when it fits, unless
  `--no-pager` or `DEV_PAGER=0` is set. With less as the pager dev adds `-+F`
  and the last line reads `& filters · / searches · q quits`: `&` narrows lines as you type.

Color is on only when the output is a terminal and `NO_COLOR` is unset.

## Flags a script declares

A project script gets a flag only when its `# flags:` line declares it. Before
a `--`, a word that starts with `-` (and is not the lone word `-`) must be a
global flag, `-h` or `--help`, or listed on the line. Anything else stops dev
before the script runs, with exit 2 and:

```
dev <verb>: unknown flag <flag>; pass it after -- to reach the script, or add it to the script's # flags: line
```

`<verb>` is the command words, a noun and its subcommand included.
`--name=value` is checked as `--name`, a declared flag's separate value
(`--days 7`) is a plain word, and words that do not start with `-` are never
refused. A value that starts with `-` is checked as a flag, so write it as
`--days=-1`.

Everything after the first `--` reaches the script untouched, so flags meant
for another tool go there: `dev test -- <args>` runs the test suites with
`<args>`.

Built-in verbs check their own flags. With `--remote`, any argument before the
`--` is refused, as the `remote` topic describes.

## Internals: launcher, dispatch and help

`dev` with no arguments is `dev help`: the project line, the verbs under task-named group headings, the topic list and a pointer line. Each verb has a description taken from the first comment line of its script. On a terminal with color the curated view and `dev help -a` draw verbs in bold, group headings in dim and each verb and topic on one line cut to the terminal width with `…`, and piped, `NO_COLOR` and `TERM=dumb` output stays plain and uncut. On a terminal the curated view (and `dev guide` with no question, once, as one text) always goes through the pager, even when it fits (`--no-pager`, `DEV_PAGER=0`, a pipe, `NO_COLOR` and `TERM=dumb` print it directly; topics keep the taller-than-the-screen rule), with `dev.ui.page` forced by `rows = 0` in `help.page_plan`. With less as the pager dev adds `-+F` to its arguments, which cancels a `-F` from `PAGER` or `LESS` that would make less quit on short text, and the paged text ends in a dim `& filters · / searches · q quits` line when the pager is less (`PAGER` unset or its first word has the basename `less`) and the pager works (a pager that fails gets the text without the line, through `dev.ui.page`'s `fallback`; `&` is less's own line filter, and dev builds no viewer). On a color terminal the closing pointer line draws its backticked spans in cyan without the backticks and is cut to the width with `…`; piped, it keeps the backticks and is not cut. `dev help -a` adds the hidden verbs and dev's own `__` helpers, `dev help <verb>` and `dev <verb> --help` print the long form, `dev <verb> -h` the description, usage and flags, and `dev help <topic>`, `dev help -k <topic>` and `dev help --topics` read topics. A topic prints as the file when standard output is not a terminal, when `NO_COLOR` is set and not empty, when `TERM` is `dumb`, and as styled Markdown through `dev.ui.markdown` otherwise (below). After rendering, `dev help <topic>` and `dev help -k <topic>` go through `dev.ui.page` (`$PAGER`, else `less -R`) when standard output is a terminal and the text has more lines than the screen has rows (`dev.term.size`), and print directly otherwise, with `dev help --no-pager ...` (the flag may stand anywhere among the arguments) or `DEV_PAGER=0` in the environment turning it off. `dev.ui.should_page(content, opts)` is the decision and `dev.ui.page(content, opts)` the pager, whose `opts` are `pager` (the command, run by `sh`), `allowed`, `interactive`, `rows` and `fallback` (the text printed when the pager fails, instead of the content); the text goes to the pager on a temporary file as its standard input, so a pager that quits early exits 0 and one that is missing or exits non-zero gets `dev: the pager failed, so the text follows without it` on standard error and the text printed directly. A `# flags: --a --b` line in a script header declares the flags that `dev help <verb>` and shell completion offer, and gates the flags that reach a project script: before a `--`, any other word that starts with `-` (not the lone `-`, a global flag, `-h` or `--help`) is refused before the script runs with `dev <verb>: unknown flag <flag>; pass it after -- to reach the script, or add it to the script's # flags: line` (exit 2, `--name=value` checked by `--name`, built-in verbs keep their own checks), so `dev test -- <args>` is how a flag the line does not declare gets through. `-h` and `--help` anywhere before a `--` are help for every verb and noun subcommand (`-h` the short form, `--help` the long one, the first one found wins; the one exception is `tools install` and `tools check` as root, where they are an unknown flag), so a script never sees them and cannot declare them in its `# flags:` line (`dev __topics check` reports one that does), while everything after a `--` reaches the verb verbatim, so `dev run -- -h` runs `cargo run -- -h`. A `# group: <name>` line sets the heading a verb is listed under (a verb with none lands in a group named after the project directory, and a built-in override keeps its built-in group), and a `# hidden` line keeps a flat verb to `dev help -a`. A `# local` line (`dev.header`'s `runs_local`, read from the script's header for the verb or noun subcommand that runs) keeps the remote default from sending that verb to ci, for a script that drives ci itself beside a same-named job; an explicit `--remote` still sends it, and `dev help <verb>` says it runs here under the default. `builtin_table` rows end in a group column, where `hidden` keeps a built-in to `dev help -a` and a subcommand row leaves it empty to take its noun's. A noun takes the group of its first subcommand script with a `# group:` line. The groups are Check your work, Share it, Set up a machine or project and Boxes, shown in that order and only when they have members, then any project group, then Hidden. Topics are markdown files with the first line `# <name>: <summary>`: built-in ones in `docs/dev/` of the dotfiles clone that holds `dev` (found through `dotfiles_root`) and project ones in `.dev/topics/`. A topic may not share a name with a verb or a built-in topic. `dev __topics check` checks the built-in topics when the project is the dotfiles clone `dev` reads them from (`DOTFILES` overrides it) and the project's topics in every project, and for each it checks the first line, those names, and that each backticked `dev` followed by words span or fenced `dev` followed by words line names a real verb or subcommand and only flags `dev __flags` lists for it, and exits 1 with `file:line` for each problem. `tests/dev/help_test.sh` runs it on the real topics and snapshots the help views of `tests/dev/fixtures/help-project/` (`UPDATE_SNAPSHOTS=1 bash tests/dev/help_test.sh` rewrites them). The global flags `-v` (or `--verbose`) and `-vv` go anywhere before a `--` and export `VERBOSE=1` (print each command before it runs) or `VERBOSE=2` (also trace every line of each bash script), and `VERBOSE` set in the environment counts the same. A command with a ci job runs remote by default: `[remote] default = "remote"` (the shipped value, also the value when nothing sets it) or `"local"` in the config files, read with `dev.config`'s `prefer_user`, so the user file beats the project file and a host picks its own default (any other value is `dev: remote.default must be "remote" or "local", got X`, exit 1). The default applies only to a command whose job `ci jobs --json` lists in the default pipeline, and never to a machine-local verb (the list below) or as root, which reads no config. A project with no `.ci/*.lua` pipeline file has no job and ci is not asked, and a command the listing does not name runs here with no message. A missing `ci` on PATH, or a `ci jobs` that exits non-zero or answers badly, fails the command with ci's error (exit code kept) and the hint `rerun, or pass --local to run it here`, so a ci deploy never moves every run onto the laptop. Local is automatic only for `CI=true`, the box marker, `--local`, `remote.default = "local"` and `DEV_REMOTE=0`. The default passes every argument to the job, before the `--` or after it. The global flag `--local`, or `DEV_REMOTE` set to `0`, `no` or `false`, runs here whatever the default, and `--remote` asks for the other way, and a command line with both is `dev: --local and --remote cannot be used together` (exit 2). Inside a ci job (`CI=true`) or a dev box (the file `/etc/ci-box` that ci writes at box creation, see "Dev boxes" in ci's README, or the path in `DEV_BOX_MARKER`, which `dev.remote.BOX_MARKER` defaults to) dev always runs here, `--remote` included, except as root. A box made before ci writes `/etc/ci-box` has no marker, so pass `--local` there. The global flag `--remote` (or `DEV_REMOTE=1`) runs the command somewhere else: dev strips `--remote` and `--detach` and hands the runner the command words and the arguments after `--`, untouched, and the runner's exit code is dev's. The runner is `.dev/__remote.lua` when the project has one (a chunk returning `function(run) -> integer`, with `run = {words, args, detach, root, verbose}`), else `ci`. The ci runner needs `ci` on PATH, checks `ci -C <root> jobs --json` for the job (`<verb>`, or the words joined by a dot for a subcommand: `<noun>.<sub>`, `<noun>.<sub>.<sub2>` one level deeper) and runs `ci -C <root> run --local --follow --job <job> -- <args>` on example-box, with `--detach` in place of `--follow`; it never falls back to a local run. An argument before the `--` is a usage error, and so is `--detach` without `--remote`. `--remote` refuses the machine-local verbs install, uninstall, restow, sync, setup, fmt, fetch, help, init, push, pull, guide, connect and every `tools`, `box`, `pi` and `antinote` subcommand with `dev <verb>: runs on this machine only, so --remote does not apply` (exit 2), whatever the runner. `bootstrap` is not refused: this repo's `.dev/__remote.lua` sends it to the `bootstrap` job of `.ci/bootstrap.lua`. That pipeline stays out of `.ci/jobs.lua` because the default one runs on every patchset. Every other command goes to `dev.remote.ci_runner`. The topic is `docs/dev/remote.md`.

Each verb is `.dev/<verb>.lua` or `.dev/<verb>.sh`. `bootstrap.sh` and the zsh completion recognize this repo by `dotfiles/bin/.local/bin/dev`. `dev` is the only entry point, and `dev help <verb>` prints a script's header, which is where each verb documents its `KEY=value` arguments (`dev setup STEPS="--install-brew"`). `dev push` and `dev pull` use jj when the repo has `.jj` and git otherwise, and `dev push` pushes only to the remote of record (the `gerrit` remote in a gerrit project, else `origin`, from the same forge setting `jj land` reads), `dev push origin` and `dev push gerrit` push to the one remote named, and `dev push` prints which forge and remote it chose and why. A flag or argument a verb does not take is a usage error that names it and exits 2.

`dotfiles/bin/.local/bin/dev` is a small launcher. At uid 0 (`$EUID` or `id -u`), before anything else, it sets `PATH` to `/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin:/sbin:/bin`, unsets `DEV_UID`, `DEV_OS`, `BASH_ENV`, `ENV` and `LUA_PATH`, `LUA_CPATH` and `LUA_INIT` with their `_5_1` and `_5_2` variants (bash has already read `BASH_ENV` by then, so this scrubs the children only), and refuses `bootstrap` with the root refusal (exit 2). It then resolves its own real path into `DEV_SELF`. `bootstrap` as the first word runs `bootstrap.sh` from the dotfiles clone, with no luajit needed, unless `--remote`, `--detach` or an enabled `DEV_REMOTE` (anything but empty, `0`, `no` or `false`) is present, or luajit is available and `--verbose`, `-v` (any number of v), `-h` or `--help` follows it before a `--`; those stay with dev's own handling. On that path the launcher drops the first `--` and passes the words after it verbatim, so `dev bootstrap --no-login`, `dev bootstrap -- --no-login` and `dev bootstrap -v -- --no-login` all give `bootstrap.sh` exactly `--no-login`, with or without luajit. With no luajit it also turns `--verbose` and `-v` words before the `--` into `VERBOSE=1` or `VERBOSE=2` (the count, at most 2) in `bootstrap.sh`'s environment and strips them from its arguments, and `-h` and `--help` reach `bootstrap.sh`, which prints its own usage. With no luajit, a non-root caller gets `dev: luajit not found. Run dev bootstrap, or install it with brew install luajit, pacman -S luajit or dnf install luajit` and exit 1. With `--remote`, `--detach` or an enabled `DEV_REMOTE` it says `dev: --remote needs luajit. Install it with brew install luajit, pacman -S luajit or dnf install luajit` instead (exit 1) and runs nothing. Otherwise it execs `luajit dotfiles/bin/.local/share/dev/main.lua`. At uid 0 luajit comes only from `/usr/bin` or `/usr/local/bin`, and when it is in neither the launcher refuses `--remote`, `--detach` and an enabled `DEV_REMOTE` with the root refusal (exit 2). A root caller without luajit and without those flags gets the root refusal (exit 2) for every command but `tools install` and `tools check`, which print `dev: as root, dev runs only on Linux` (exit 2) off Linux and `dev: dev tools needs luajit in /usr/bin or /usr/local/bin` (exit 1) on it, decided by the launcher in bash from the words after the `-v` and `--verbose` flags, before anything is read. `main.lua` builds its `package.path` from its own location only and calls `dev.cli`, which parses the global flags, applies the root gate, resolves the verb through `dev.registry`, refuses a flag the verb's `# flags:` line does not declare (not with `--remote`, whose own check refuses every argument before a `--`), runs a `.lua` verb in process (`chunk(ctx)`, with `.dev/lua` added to `package.path` unless root, an error or a syntax error printed as `dev <verb>: <message>` with exit 1), execs a `.sh` verb, and runs `--remote` through `dev.remote`. `__verbs`, `__subs`, `__flags` and `__topics check` are served by `dev.complete` and `dev.topics`. The project-type built-ins (`lint`, `fmt`, `test`, `build`, `run`, `fetch`) run in process through `dev.cmd.types`, and `deploy`, `guide` and `bootstrap` through `dev.cmd.misc`. `sync` runs through `dev.cmd.sync` over `dev.templates`, and `push` and `pull` run through `dev.cmd.push` and `dev.cmd.pull`, with the backend and the forge setting in `dev.vcs` and `dev.forge`, and `dev help push` and `dev help pull` print their commands from the same code. `tools install` and `tools check` run through `dev.cmd.tools` and, as root, `dev.root`. `init` runs through `dev.cmd.init`. A word the registry does not know is `dev: unknown verb <word>` with the curated help on stderr (exit 2). A test seam (`tests/lua/fake_env.lua` through `LUA_INIT`) can fake the uid and system name for a user but never loads at uid 0.
